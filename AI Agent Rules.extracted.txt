AI Agent Rules — Iron Merchant Management SystemThese rules must be followed by any AI coding agent working on this project. The goal is to write clean, simple, efficient, maintainable code without unnecessary complexity.1. Understand the project before codingBefore implementing any feature:Read the Iron_Merchant_Software_Core_Understanding document.Understand the business requirements and existing application architecture.Inspect the project folder structure.Read package.json and check installed dependencies and versions.Inspect existing components, hooks, utilities, types, database schema, migrations, and RPC functions.Check existing coding conventions and follow them.Identify which files need to change before starting implementation.Never start coding without understanding the existing codebase.2. Skills inspection is mandatoryBefore writing code for any feature:Check all skills available to the AI agent.Read the complete instructions of skills relevant to the requested feature.Read any supporting documentation provided by those skills.Analyze the skills and determine how they can help implement the feature efficiently.Use relevant skills during implementation.Do not force irrelevant skills into the workflow.For example:For database tasks, inspect relevant database and Supabase skills.For frontend tasks, inspect relevant React, Next.js, and UI skills.For testing tasks, inspect relevant testing skills.For accessibility tasks, inspect relevant accessibility skills.If no relevant skill is available, proceed using the project's existing conventions and reliable documentation.Do not just check which skills are available. Read and understand the relevant skills before coding.3. Write clean and simple codeWrite readable, maintainable, and understandable code.Do not write clever or unnecessarily complicated code.Prefer simple solutions over complex abstractions.Avoid unnecessary one-liners and deeply nested conditions.Use meaningful variable, function, and component names.Keep functions focused and reasonably small.Avoid duplicate code.Remove unused imports, variables, functions, and debugging statements.Add comments only when they explain something important.Do not write code just to reduce the number of lines.Do not over-engineer simple features.The next developer should be able to understand the code without spending hours figuring out how it works.4. No prop drillingDo not pass the same data through multiple component levels just to reach a deeply nested component.Follow these rules:Keep component state local when possible.Use React Context for genuinely shared state.Create feature-specific providers instead of one giant global context.Use custom hooks to organize reusable feature logic.Prefer component composition when it makes the architecture cleaner.Do not introduce Redux or another state-management library without a genuine need.Do not use Context for everything.The goal is a clean component architecture with minimal unnecessary dependencies between components.5. Code according to the featureWhen implementing a feature:Understand exactly what the feature should do.Identify its required UI, business logic, database operations, and validations.Implement only what is required.Reuse existing components and utilities where appropriate.Do not modify unrelated features.Do not redesign existing screens unless requested.Do not add unnecessary functionality.Do not create duplicate implementations of existing functionality.For example, when implementing a purchase feature, complete its actual workflow:Purchase form.Supplier selection.Product selection.Individual shaft weight and length entry.Purchase cost calculation.Landed-cost allocation.Database transaction.Inventory update.Weighted average cost recalculation.Supplier account and accounting updates.Do not just create a purchase form and call the feature complete.6. Follow the existing technology stackUse the project's existing technology and conventions.Recommended project stack:Frontend: Next.js App RouterLanguage: TypeScriptUI: ReactStyling: Tailwind CSSBackend and Database: Supabase PostgreSQLAuthentication: Supabase AuthStorage: Supabase Storage when requiredRules:Check existing dependencies before installing new packages.Avoid unnecessary libraries.Do not upgrade packages without a reason.Use TypeScript properly.Avoid any.Use Server Components by default.Use Client Components only when interactivity is needed.Keep server-side operations separate from client-side components.Never expose private environment variables or service-role keys in frontend code.7. React component rulesEach component should have a clear responsibility.Avoid unnecessarily large components.Separate reusable UI components from feature-specific components.Keep database operations out of presentation components.Use custom hooks when they genuinely simplify reusable logic.Avoid unnecessary useEffect.Do not store derived values in separate state variables.Avoid unnecessary re-renders.Use useMemo and useCallback only when they provide a real benefit.Handle loading, empty, error, success, and disabled states.Make interfaces responsive.Follow consistent design patterns throughout the application.8. Database rulesThe database is the source of truth for business operations.Use PostgreSQL through Supabase.Use UUIDs for primary keys.Use foreign keys and appropriate constraints.Use indexes for frequently queried columns.Use NUMERIC for money, weights, lengths, and rates.Never use floating-point types for financial calculations.Use database transactions for operations involving multiple tables.Use RPC functions for important business operations.Prevent negative stock and invalid inventory states.Never trust calculations sent by the frontend without server/database validation.Never allow frontend code to directly modify important aggregate inventory or accounting balances.Keep database migrations organized and documented.9. Important business rulesThese rules must never be violated.InventoryEvery physical iron shaft must have a unique piece code.Every shaft must have its actual measured weight and length.Each cut piece must have its own inventory record.Preserve the relationship between the original shaft and its cut pieces.A split shaft cannot be sold or cut again.Weighted Average CostUse:New WAC = (Existing Inventory Value + New Landed Purchase Cost) / (Existing Inventory KG + New Purchase KG)WAC applies only to usable shaft inventory.Scrap must be maintained separately.Update WAC when purchases are confirmed.Reduce inventory value when stock is sold.Record the appropriate cost of goods sold.CuttingCutting consumes an existing shaft.Cutting creates new child pieces.Each child piece has its own actual measured length and weight.Scrap must be recorded separately.Cutting must not create sales revenue or profit.Record unexplained weight differences.Any actual cutting loss must be accounted for.Do not silently discard inventory quantity or value.SalesThere are three sale types:Full shaft sale.Cut piece sale.Scrap sale.Rules:Full shafts use the full-shaft selling rate per kg.Cut pieces use the cut-piece selling rate per kg.Scrap uses a separate scrap selling rate.Sales amount is calculated using actual sold weight multiplied by the applicable rate.Store the applied rate on the invoice line.Future price changes must not modify previous invoices.Never sell the same inventory piece twice.PaymentsPayments must be separate from invoices.Support partial payments.Support one payment allocated across multiple invoices.Support customer advances and unapplied payments.Calculate outstanding balances from actual transactions and allocations.Never manually overwrite calculated outstanding balances.AccountingUse double-entry accounting.Every journal entry must have equal debit and credit totals.Purchases, sales, payments, expenses, and cutting losses must be properly accounted for.Inventory changes and accounting entries must happen in the same database transaction.10. Security rulesUse Supabase Auth.The current system has one owner/admin.Enable Row Level Security on all owner-scoped tables.Users must only access their own business records.Never expose the Supabase service-role key.Validate ownership inside sensitive database functions.Use secure RPC permissions.Keep confirmed financial transactions and stock movements protected from direct modification.Audit important business operations.Security must be enforced at the database and server level, not just through frontend visibility.11. Error handling and validationValidate all user inputs.Validate important business rules on the server/database.Show understandable error messages.Do not expose database errors or stack traces to users.Prevent duplicate form submissions.Handle network failures.Handle expired sessions.Provide loading indicators during database operations.Never show success before the operation has actually completed.12. Performance rulesFetch only the data required by a feature.Avoid unnecessary database requests.Avoid N+1 queries.Use pagination for large inventory and transaction lists.Add indexes based on actual query requirements.Avoid unnecessary state updates and component re-renders.Do not optimize prematurely.Prioritize data accuracy and financial consistency over small performance improvements.13. Testing rulesAfter implementing a feature:Run TypeScript checks.Run linting.Run relevant tests.Test database operations.Test error scenarios.Test responsive layouts.Check that existing features still work.Review the final code changes.For important business operations, test scenarios such as:Preventing duplicate sales.Preventing duplicate cutting.Correct WAC calculations.Correct cutting and scrap calculations.Partial payments.Payment allocations.Correct customer balances.Correct supplier balances.Balanced accounting entries.Reversal of transactions.RLS security.Never claim that something works unless it has actually been tested.14. Git and file managementCheck Git status before making changes.Never overwrite unrelated user changes.Do not delete files without a reason.Do not reset or clean the repository without permission.Keep changes limited to the requested feature.Review the final Git diff.Do not commit or push unless requested.15. Required workflow for every featureFollow this process:Understand the requirement. Read the feature request and relevant business documentation.Inspect available skills. Read and analyze relevant skills before coding.Inspect the codebase. Understand existing files, components, database structure, and conventions.Plan the implementation. Identify the smallest set of required changes.Implement the feature. Write simple, clean, maintainable code.Validate the feature. Run tests, type checks, linting, and relevant database checks.Review the changes. Check for bugs, duplicate code, security problems, and unrelated modifications.Report completion. Explain what was implemented and what remains.16. Final response after completing a taskAfter implementing a feature, provide a short report containing:Implemented: What functionality was added.Files changed: Which important files were created or modified.Database changes: Any migrations, tables, RPCs, or policies added.Testing: Which commands and tests were actually run.Remaining work: Any incomplete functionality or decisions requiring approval.Do not claim something is production-ready without proper testing and review.Golden RuleBefore coding, understand the feature, inspect all available skills, analyze the existing code, and understand the business requirements. Then write the simplest complete solution.Write clean code. Avoid prop drilling. Do not over-engineer. Do not write clever code. Do not modify unrelated features. Always prioritize correctness, readability, security, and maintainability.
